# Tracking owner fence 0.1D — epoch lifecycle

Status: specified, not implemented. No historical value is invented.
`OWNER_EPOCH_LIFECYCLE_DEFINED=YES`.

`transport.transport_executions` has no `owner_epoch` column at migration head `000105`. Existing rows are not backfilled.

## 1. Creation

A future shipment insert, the statement at `services/shipment-service/internal/repository/transport_execution_repository.go:296-301`, sets `owner_epoch` to `1` in the same transaction that inserts the execution. The value is generated by the database statement. It is not taken from the HTTP caller, the Kafka payload, or `event_seq`.

Rows that already exist when the column is added stay null. A null epoch is not treated as `1`.

## 2. What increments it

An increment happens only in a shipment transaction that is the authorized owner change for that execution. The statement is `owner_epoch = owner_epoch + 1` on the row locked by that update. The new value is one greater than the locked value.

The current production updates do not change `operating_tenant_id`. They change `current_revision_id` or `event_seq` (`transport_execution_repository.go:92-96`, `transport_execution_successor_repository.go:172-176`, `transport_execution_successor_repository.go:457-461`, `transport_execution_command_repository.go:1224-1228`, `transport_execution_command_repository.go:1342-1346`). Those statements must not increment `owner_epoch`. `event_seq` remains the event counter.

No owner-change command exists in this tree. Until a controller names that command, the only epoch write specified here is the insert value `1`.

## 3. Decrease

The epoch does not decrease. A future trigger rejects `NEW.owner_epoch` when `OLD.owner_epoch` is not null and the new value is lower. A replay of an older event does not write the smaller epoch back onto the execution row or onto the tracking state row.

That trigger is not in the migration chain. A design sentence does not stop an `UPDATE`. Monotonicity stays in `OPEN_RISKS` until the trigger exists and a test shows a decrease failing.

A null `owner_epoch` stays null. It is not read as `1`, and it is not a reason to skip the event. An event with a null epoch, and an execution row that returns a null epoch, are `NON_TERMINAL`. The tracking transaction rolls back. No state update remains and the offset stays where it was.

## 4. Kafka

`emitExecutionEvent` already updates `event_seq` and then builds the payload in one transaction (`transport_execution_command_repository.go:1224-1244`). The payload gains `owner_epoch` from the same locked row. The outbox id and the payload `event_id` stay different, as they are today. The header `eventType` is not the epoch authority.

A consumer that sees a payload without `owner_epoch` classifies the record `NON_TERMINAL` and does not commit the offset.

## 5. Tenant

`transport.lock_execution_owner` returns the stored `operating_tenant_id`. The event claim must equal that value. `X-Tenant-ID` on the tracking context call is the payload tenant today (`services/tracking-service/internal/service/shipment_context_client.go:39`). Under this lifecycle that header is not the owner check. A mismatch rolls the tracking transaction back and leaves the stored tenant unchanged.

## 6. Historical events

Events produced before the column exists have no epoch. Inbox rows have no hash, size, or epoch. State rows have no `last_event_id`. Replay of those records stays `NON_TERMINAL`.

Forbidden repairs:

- setting null epochs to `1` because the row exists;
- copying `event_seq` into `owner_epoch`;
- choosing the inbox `event_id` with the highest sequence as `last_event_id`.

## 7. Restart and stale events

A crash before commit rolls the database transaction back. The execution epoch, the state row, and the inbox stay as the last committed values. `CommitRecords` has not run for that attempt when the crash is before `execution_event_consumer.go:60-61`.

A crash after commit and before `CommitRecords` leaves the proof in place. Restart reads it. The offset advances once when the proof matches `event_id`, hash, size, sequence, tenant, and epoch. A null `last_event_id` does not match.

A stale event is one whose epoch is absent or different from the epoch returned under the execution lock. The attempt rolls back. The partition stays on that offset. A later event with the locked epoch can still be applied. The stale record is not skipped by advancing the offset.
