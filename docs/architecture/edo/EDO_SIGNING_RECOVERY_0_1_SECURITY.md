# EDO signing recovery 0.1 — idempotency, concurrency, and security

## Idempotency facts

Session signatures do not take an idempotency key (`services/document-service/internal/domain/signing_session.go:65-72`). Two accepted calls can insert two signature rows while the session remains open. The completed count is protected by compare-and-set on the locked row (`signing_repository.go:295-306`), which stops a lost update. It does not stop a duplicate legal action.

Attachment signatures carry an idempotency key (`attachment_service.go:281`). That key is not the session-signature contract.

A document content hash is not the operation id. The same hash can be signed by another party, in another session, or after a rejected attempt.

## Proposed operation identity

A future signing operation is identified by all of:

- operation id, generated by the server for a new attempt
- tenant id from the verified caller
- document id
- document version at preparation
- content hash of the bytes that were prepared
- signer user id and signer company id
- provider reference, empty until an adapter returns one

The HTTP `Idempotency-Key` of a repeated request maps to one operation id. It does not allocate a new one. A new signing attempt after recovery gets a new operation id even when the document hash is unchanged.

## What each repeat means

| Repeat | Meaning | Effect |
| --- | --- | --- |
| Same HTTP request, same key, same body | Replay | Return the stored result. Write nothing |
| Technical retry of a local transaction that rolled back | Same operation id, no signature row | Insert once |
| Technical retry while `RESULT_UNKNOWN` | Same operation id, provider outcome not proven | Do not call the provider again unless that interface documents idempotency for this id |
| New signing operation | New operation id after the previous session is terminal and authorization is current | New session, as `CreateSession` does today |
| Confirmation replay | Same provider reference | No second confirmation |
| Manual recovery | Reviewer decision on `MANUAL_REVIEW_REQUIRED` | No signature is created by the reviewer role |

## Retry by state

| State | Same operation id | New provider call | New operation id |
| --- | --- | --- | --- |
| `CREATED` or `PREPARED` | Replay preparation | No | No |
| `SIGNING` with a committed local signature | Replay that signature | No | No |
| `RESULT_UNKNOWN` | Replay the unknown marker | Only with a proven idempotent provider contract | No |
| `EXPIRED` and document returned to `READY_FOR_SIGNING` | Do not resurrect the old session | No | Yes, through a new `CreateSession` after authorization is checked again |
| `SIGNED` or `CONFIRMED` | Replay | No | No |
| `FAILED_FINAL` | Replay the failure | No | No |
| `MANUAL_REVIEW_REQUIRED` | Replay the hold | No | No |

## Concurrency

Current locks are the document row, then the session row (`signing_repository.go:220-230`). Recovery locks the document, then all sessions of that document ordered by id (`signing_repository.go:352-363`). A later worker must keep that order.

A stale worker is one whose fencing token, or the compare-and-set version, no longer matches. It commits nothing. A late provider response is applied only when the operation id, tenant, version, and hash match. A contradictory status becomes `MANUAL_REVIEW_REQUIRED` and does not overwrite `SIGNED` with a failure for a different attempt.

This design does not promise exactly-once for an external provider. It promises at-least-once local processing with idempotent transitions. External exactly-once is `NOT_VERIFIED` because no provider contract exists.

## Tenant isolation

Every recovery read and write includes the tenant of the authorized caller and the document. A foreign id returns the same not-found result as a missing id (`signing_recovery.go:45-47`). Cross-tenant lookup is forbidden for the future reconciler as well.

Today the HTTP handler takes the tenant from `X-Tenant-ID` (`signing_handler.go:103`). That header is not, by itself, a recovered caller's authority. Pull request #360 requires a server-confirmed caller before a document write. Recovery HTTP stays 403 even after that caller exists, until a later stage is authorized.

## Authorization

Creating a session and adding a signature are sensitive transitions. A grant checked at preparation is checked again before a new operation. Expiry of the session does not preserve the right to sign. Revocation of the signer, which is `NOT_IMPLEMENTED` as a live check, must block a new session.

`PLATFORM_ADMIN` is not authority to sign as a party. The current gateway wildcard allows that role to reach document routes when authentication is enabled. This recovery design does not treat that reachability as a signing right. The role matrix in pull request #371 marks `document.sign` as `SEPARATE_AUTHORITY_REQUIRED`.

Recovery permissions, proposed and not granted:

| Action | Who |
| --- | --- |
| Read operation state | A caller who can read that document in that tenant and company |
| Request reconciliation | The document owner company member who holds the future reconcile permission, or the worker using the service credential |
| Resume technical processing of `RESULT_UNKNOWN` | The reconciler. It does not create a new signature without provider evidence |
| Create a new signing operation | The current signer grant. Not the old session |
| Resolve `MANUAL_REVIEW_REQUIRED` | A named reviewer permission. The reviewer does not apply the party's key |

## Integrity and secrets

A legally significant attempt must store the document version and the hash of the bytes that were signed. The current signature row stores `signature_payload_path` and an optional certificate fingerprint, and it marks verification `VALID` without a check (`signing_repository.go:264-287`). That is not the integrity record this design requires.

Logs, this document, and future fixtures must not contain private keys, signing tokens, or certificate private material. Attachment code already rejects private-key material in a reference (`attachment_service.go:303-305`). Tests use labels and hashes, not real certificates.

## Audit

The proposed events are listed in the test plan and the ADR. They are `NOT_IMPLEMENTED` for signing sessions. `documents.attachment_audit_events` is a different journal (`attachment_repository.go:216`).

The signing journal must be append-only for the application role: insert, no update or delete of the event payload. Whether the database role already enforces that was `NOT_VERIFIED` in this pass. No live database was queried.
